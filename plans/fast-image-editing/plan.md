# pic-cli：快速、参数化的图像编辑

状态：需求与架构草案，尚未实现。用户希望刚才列出的三类功能全部覆盖：照片调整、图层合成、智能编辑。具体 Photoshop 兼容深度、目标平台和基准硬件待确认。

## 意图

用户希望使用 Rust 开发供 agent 调用的 pic-cli，支持部分 Photoshop 式图像编辑功能，通过传入参数直接得到结果，响应速度是核心要求。CLI 负责执行明确的图像操作；调用方负责选择操作及参数。基础编辑应能本地运行，性能评价包含命令启动、文件读取、解码、处理、编码和写入。

已确认：Rust、CLI、agent 可调用、参数化编辑、速度优先；针对首版三类功能的选择，用户回答“全部对齐？”，因此方案按三类全部纳入目标更新。尚未确认：每类的具体功能集合、与 Photoshop 的参数及文件兼容深度、常见图片尺寸、目标平台、模型执行环境。下文的具体功能清单和性能数字仍是建议，不代表已经实测达到。

## 仓库现状

- 根目录目前只有 `AGENTS.md`、`.gitignore` 和参考资料；没有 `Cargo.toml`、产品源码或现成构建、测试命令。
- `reference/` 已有 gimpish、Compositor、Photoshop MCP、CLI-Anything、AgentBrush、libvips 和 sharp 的源码。

## 目标与首版覆盖范围

首版按三类全部覆盖设计，分阶段交付以便验证。阶段顺序是实现依赖，不把智能编辑自动降为可省略功能；最终验收应包含三类能力的真实端到端执行。

| 阶段 | 功能 | 参数化方式 |
| --- | --- | --- |
| P0 | 图片信息、裁剪、缩放、旋转、翻转、画布大小、PNG/JPEG 导出 | 明确尺寸、坐标、插值方式和输出参数 |
| P0 | 曝光、亮度、对比度、饱和度、色阶、曲线、灰度、反相、模糊、锐化 | 参数定义有单位、范围和默认值；执行顺序确定 |
| P0 | 有序操作管线、JSON 输出、错误码、阶段耗时 | 单操作命令与 JSON 管线调用同一执行核心 |
| P1 | 多图合成、位置与变换、不透明度、混合模式、外部蒙版、选区 | 首批混合模式建议 normal、multiply、screen、overlay；明确蒙版与选区的坐标空间 |
| P1 | 文字、图层组、剪贴蒙版、调整层、可保存工程、预览和撤销 | 明确字体来源、稳定图层 ID、素材路径、版本化工程与跨命令历史 |
| P2 | 自动抠图、主体分割、物体移除与修复 | 输入图片、可选区域/蒙版、模型、执行后端；输出图片、蒙版及执行信息 |
| P2 | 生成式填充与扩图 | 输入图片、区域/蒙版、提示词、输出范围和后端支持的生成参数 |

首版建议先覆盖 8-bit sRGB 的 PNG/JPEG。透明度、EXIF 方向和工作色彩空间必须有明确约定。其他格式、位深或色彩空间应明确处理能力，不能悄悄改变颜色或丢失透明度。

模型功能允许通过本地运行时或远端服务执行，具体选择取决于效果、硬件、成本和时延评估。使用 Rust 编写 CLI 不要求所有图像算法和模型运行时都重新用 Rust 实现。普通编辑保持独立可用，智能编辑所需模型或凭据缺失时准确报告当前能力。

兼容性需要单独列矩阵：功能覆盖、参数语义、输出质量、文件保真、执行时延分别验收。“三类都覆盖”尚不能被当作 Photoshop 每个功能、每个参数和所有 PSD 文件完全兼容的已确认要求。完整 PSD 无损往返、RAW、专业印刷色彩、完整笔刷系统、插件和桌面 GUI 暂列为待确认的扩展范围。

能力查询必须区分已支持、部分支持和尚未实现。生成式操作的效果通过任务结果验收；不能保证与 Photoshop 的专有模型生成相同像素，即便后端提供随机种子也不能跨模型保证一致。

## 方案

### 1. 单操作和多步处理共享接口

以下为拟定接口，尚未实现：

```sh
pic-cli resize photo.jpg --width 1600 --output resized.jpg
pic-cli adjust photo.jpg --exposure 0.5 --saturation 1.1 --output adjusted.jpg
pic-cli composite background.png --overlay subject.png --x 100 --y 80 --opacity 0.8 --output result.png
pic-cli run --input photo.jpg --pipeline pipeline.json --output result.jpg --json
pic-cli remove-bg photo.jpg --backend local --output cutout.png
pic-cli erase photo.jpg --mask object-mask.png --backend local --output repaired.png
pic-cli fill photo.jpg --mask region.png --prompt "木质桌面" --backend remote --output filled.png
```

智能编辑示例表达目标接口，不代表对应后端或模型已经选定。具体后端必须提供实际能力声明；不支持的参数在执行前明确拒绝。

`exposure` 建议使用 EV；`saturation` 建议使用倍率，1 为不变。CLI 和 JSON 必须使用相同语义。多步管线示例：

```json
{
  "version": 1,
  "operations": [
    { "op": "resize", "width": 1600 },
    { "op": "adjust", "exposure": 0.5, "saturation": 1.1 },
    { "op": "composite", "source": "logo.png", "x": 24, "y": 24, "opacity": 0.8 }
  ]
}
```

按数组顺序执行，坐标相对于该步骤的当前画布。只有证明等价的操作才能融合或重排。同一输入尽量只解码一次，最终只编码一次；中间结果保留在内存中。资源路径以管线文件所在目录解析，命令行输入输出路径以当前工作目录解析，并在返回结果中给出实际输出路径。

轻量图层工程与一次性处理共用操作核心；普通文件处理无需创建工程。工程格式参考 gimpish 与 Compositor，保存稳定图层 ID、源素材、变换、蒙版和参数。需要跨命令保留的历史必须落盘，不能依赖上一次 CLI 进程的内存。

### 2. Rust 实现与引擎选择

拟建立 `pic-core` 处理库与 `pic-cli` 命令入口。核心按 codec、operation、pipeline、composite、document 分模块，CLI 负责参数解析、结构化输出和退出码。另设智能编辑后端接口，管理能力查询、模型加载、区域/蒙版输入、生成或修复结果以及错误映射。

首轮验证以 `image` 处理 PNG/JPEG 读写、`fast_image_resize` 处理缩放为起点；自有操作共享统一的像素表示和参数类型。按需评估 `imageproc`，避免为了少量功能引入无关处理链。高成本像素运算再根据实测加入 SIMD 或受控的线程并行。

libvips 作为性能对照及候选原生后端，在相同输出尺寸、采样、颜色与质量设置下比较。若特定负载明显受益，再决定是否通过 Rust 绑定或 FFI 引入；不在第一版同时维护多套完整后端。

公开资料确认：`image` 提供格式编解码和基础处理；`fast_image_resize` 提供 SIMD 缩放及可选 Rayon 并行，但线性色彩空间转换需调用方明确处理。这些是能力依据，不能替代 pic-cli 的端到端性能验证。

- [image](https://github.com/image-rs/image)
- [fast_image_resize](https://github.com/Cykooz/fast_image_resize)
- [imageproc](https://github.com/image-rs/imageproc)

### 3. 速度设计

- 编译后的 CLI 直接调用处理核心；普通操作启动路径只加载所需组件。
- 解码后的图片在操作间复用，减少整图复制和中间文件；点操作按等价性合并像素遍历。
- 缩放与合成正确处理 alpha，避免透明边缘出现黑边；先固定颜色与采样语义，再比较性能。
- 并行策略限制总线程数，避免“批量图片并行 × 每张图并行”造成过度争抢；小图片保留低开销路径。
- 编码纳入优化范围。PNG 的压缩等级影响耗时和文件大小，JPEG 质量影响耗时与输出质量，两者分别定义参数和基准。
- 图层工程采用素材缓存；分块、受影响区域更新与不可变快照参考 Compositor，具体优化顺序取决于实际内存和处理瓶颈。
- 模型操作使用独立能力模块，分别报告模型加载、推理和远端等待耗时。首轮模型验证就测连续调用；需要复用模型时，可选本地 worker 承担常驻模型，CLI 仍是统一入口。
- 智能编辑保持单条命令可调用，但不套用普通像素操作的时间预算。长操作提供进度与超时信息；若后续增加异步任务接口，接收任务与成功完成必须是不同状态。

### 4. agent 使用约定

- `--help` 与能力查询列出支持的操作及参数；提供 `info` 获取尺寸、格式和颜色信息。
- `--json` 输出稳定、带版本的结果结构，包括成功状态、输出文件、尺寸、警告、错误码与阶段耗时；运行日志写入 stderr。
- 操作目标和输入输出路径明确，失败返回非零退出码，不弹出交互式提示。
- 支持输出预览和检查实际像素结果。工程元数据更新成功不能替代渲染结果验证。
- 输出采用临时文件完成后替换目标，防止处理失败留下半成品；覆盖行为由明确参数控制。

## 性能验收

首先登记基准机器的 CPU、内存、操作系统、磁盘、线程数、编译器和构建配置。使用 release 构建和固定素材，分别记录新进程启动、文件缓存状态、解码、处理、编码、总耗时与峰值内存。至少重复 30 次，报告 p50 与 p95。

下列为待基准确认的建议目标，不是当前性能承诺：

| 工作负载 | 建议端到端 p95 目标 |
| --- | --- |
| `--version`，本地二进制，文件缓存已热 | 30 ms 内 |
| 1920×1080 JPEG → 缩放、曝光、饱和度 → JPEG | 300 ms 内 |
| 3840×2160 JPEG → 基础调整 → JPEG | 1 s 内 |

固定 JPEG 编码质量与缩放滤镜；总耗时包含新进程启动和最终文件关闭，不包含等待磁盘持久化的额外 `fsync` 保证。另测 PNG 透明图、4K 多图层合成和大半径模糊，取得基线后分别设门槛；不能把基础调整的预算套到所有功能上。

智能编辑单独建立测试集，记录模型/服务版本、设备、输入尺寸、推理参数、模型已缓存与未加载时的耗时，并同时检查抠图边缘、选区外保真及修复效果。模型下载、冷加载、暖推理、远端排队/传输各自报告。具体模型未定前不承诺统一的毫秒级指标。

与 libvips 或其他工具比较时校验实际画质与颜色行为，不能通过降低分辨率、采样精度或编码质量来达成时间指标。未实测前不宣称比 Photoshop 或现有 CLI 更快。

## 校验

仓库目前没有可运行的 Rust 校验目标。建立工程后计划执行：

```sh
cargo fmt --all -- --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
cargo build --release
```

功能验证覆盖：操作顺序、坐标、EXIF 方向、透明边缘、混合模式、蒙版、无效参数、真实文件输入输出及 JSON 结果。对调色和合成使用可解析预期值的小型像素样本，对复杂渲染采用固定素材的输出比较。性能测量另跑实际二进制，避免只测内存中的单个函数。

基础内核里程碑：导入背景和主体 → 使用现成蒙版合成 → 添加文字 → 保存工程并重新打开修改 → 导出，校验尺寸、透明度、位置、历史和总耗时。

完整首版增加真实智能编辑验收：自动抠图并保存可编辑蒙版 → 调色与合成 → 根据区域移除物体 → 生成式填充或扩图 → 导出，分别检查每项已承诺能力的效果和耗时。可用固定响应测试接口契约，但不能用 mock 后端或仅有命令壳替代实际模型/服务验收。生成测试采用人工认可的任务样例与区域保真检查，不要求不同生成模型逐像素相同。

## 风险与开放问题

- 三类功能均纳入目标，具体 Photoshop 兼容深度、图片尺寸和目标机器尚未确认；这些决定实际功能清单及性能门槛。
- 模型选择、可用 GPU、远端服务凭据和使用成本尚未确定；智能编辑的效果与时延要在选型阶段验证。
- Rust 本身不能保证低延迟；编解码、内存带宽、算法、复制和启动路径都需测量。
- Photoshop 的调色、混合与字体行为存在具体语义；以本项目明确的参数和输出规范验收，兼容性要求需单独定义。
- 中文文字需要字体选择与排版能力，不能把简单字符绘制当作完整文字排版。
- 4K RGBA8 单张像素缓冲约 31.6 MiB，多图层与浮点中间缓冲会显著增加内存；建立工程缓存和历史前先明确预算。
